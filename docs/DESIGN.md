# Design decisions

Every non-obvious decision in this harness, with the failure mode that
motivated it. These are written as portable engineering lessons: each one
was paid for at least once, and each transfers to any system with the same
shape -- small files, links between them, an index, and more than one
environment running the tooling.

## Derived-state index over hand-maintained dual-write

`MEMORY.md` is generated by `scripts/memory-index.sh` from file frontmatter.
It is never edited by hand, and the health gate hard-fails when the
committed index differs from regeneration.

The alternative -- an index maintained alongside the files -- is a
dual-write, and dual-writes have a known failure mode: the two writes are
not atomic, so every add, delete, or description change is an opportunity
to update one side and forget the other. The observable symptom is orphan
rate: index entries pointing at files that no longer exist, and files that
never made it into the index. Orphans accumulate silently because nothing
consumes the index strictly enough to notice.

A derived index eliminates the class rather than policing it. The index is
a pure function of the corpus; regeneration is idempotent; drift is
mechanically detectable (`diff` against regeneration) and mechanically
repairable (regenerate). The general lesson: when state B is a function of
state A, derive B -- do not maintain B and check it against A. Checking is
strictly weaker than deriving; deriving makes the drift impossible.

Sort order is type group, then filename -- deliberately not recency. File
mtimes are not stable across clones, and recency is recoverable from git
log, while the property that each new memory diffs as exactly one line is
not recoverable from a recency sort. Choose sort keys that are stable under
clone and that minimize diff noise.

## Frontmatter name as the sole immutable link identity

Each memory declares a kebab-case `name:` in frontmatter. Wikilinks
(`[[target]]`) resolve against the union of names and filenames sans
extension. The name is immutable for the life of the memory.

Rationale: something has to be the join key, and everything mutable makes a
bad one. Titles get reworded; descriptions get sharpened; dates go stale.
The moment the join key changes, every inbound reference dangles -- and in
a corpus written by an agent across many sessions, nobody is watching the
inbound references. So the identity is a slug, the slug never changes, and
everything mutable lives in fields that nothing links against.

Two corollaries:

- **Supersede, never rename.** A memory whose content became wrong is not
  renamed or rewritten into something else; a new memory is written that
  states the correction, and the old one either points at it or is left as
  historical record. The old name keeps resolving forever, so no link ever
  breaks retroactively. This is the same discipline as never rewriting
  shared git history: identities that others may hold references to are
  append-only.

- **Grandfather allowlist for legacy divergence.** A rule adopted after a
  corpus already exists will have violators that cannot be fixed without
  breaking the rule itself (renaming a legacy file to fix its slug breaks
  its links -- the exact harm the rule exists to prevent). The pattern:
  a shell variable in the checker (`GRANDFATHER`, `GRANDFATHER_DIVERGED`),
  one slug per line, that exempts named legacy files from the check. It
  ships empty: a fresh adoption has no pre-rule history. The critical
  property is that the allowlist is frozen at adoption time -- adding an
  entry for a new file is using the escape hatch as a policy change, which
  the comments in the script explicitly forbid. New violations are fixed;
  old ones are named and tolerated.

## Normalized identity comparison

The name-identity check does not require the frontmatter name to equal the
filename byte-for-byte. Both are first normalized -- type prefix stripped
(`feedback`/`project`/`reference`/`tmp` plus `-` or `_`), underscores
folded to dashes -- and the normalized forms are compared.

Strict basename equality fails on legacy corpora: files created under older
conventions carry type prefixes and underscore separators in the filename
while the frontmatter name uses the clean slug. Those are the same identity
spelled two ways, and flagging them buries the real signal in noise. What
the check must catch is a true lineage fork: a frontmatter name that
denotes a different memory than the filename does, so that a grep for the
slug misses the name and a grep for the name misses the slug -- at which
point the dedup check ("does a memory for this already exist?") silently
answers no and a duplicate lineage is born. Normalization separates the
two cases: spelling variants collapse, forks survive and fail hard.

The same normalization powers the near-miss wikilink check: a link that
resolves only after normalization is a typo at the link site, not an
aspiration, and is failed hard with a suggestion -- fix the link, not the
file.

## Fail-closed toolchain preflight

`memory-health.sh` dies (exit 2) if ripgrep is not on PATH, before running
a single check.

The trap this closes: the wikilink and checkpoint checks are built on `rg`.
If `rg` is missing and the failure is soft, those checks return empty
result sets -- which is indistinguishable from "no broken links". A sick
store reports healthy, and it reports healthy precisely in the environments
most likely to be missing the tool: fresh CI runners (ubuntu images do not
ship ripgrep) and scheduler contexts with a bare PATH. A gate that can be
silently disarmed by its own environment is not a gate.

The general rule: when a checker's dependencies are absent, the checker
must report "cannot check" as a failure, never "nothing found". The CI
workflow installs ripgrep explicitly, and the scripts prepend the common
local bin directories to PATH for scheduler contexts -- but those are
conveniences; the preflight remains the authority.

## Collation pinning

Every script exports `LC_ALL=C` before doing anything else.

The failure this fixes: `sort` order is locale-dependent, and the harness
runs under at least three locales -- an interactive macOS shell (typically
a UTF-8 locale), launchd (bare environment), and a Linux CI runner. An
unpinned collation produced index output whose sort order drifted across
those environments: the same store regenerated on two machines gave two
byte-different indexes, and the health gate's drift check -- correctly --
failed, blaming the store for a property of the environment. The line-set
algebra in the checker (`sort -u`, `uniq`, `grep -x` against sorted files)
has the same sensitivity.

Lesson: any script whose output is compared byte-for-byte across
environments, or that feeds `sort` output into set operations, must pin its
collation. `LC_ALL=C` is the only portable pin.

## Delimiter-bounded frontmatter parsing

Frontmatter is extracted by an awk program that takes only the lines
between the leading `---` delimiter pair, and nothing else:

    awk 'NR==1{if($0!="---")exit; next} /^---$/{exit} {print}'

The naive alternative -- grepping the whole file for `^name:` -- has a
self-referential failure mode: a memory that documents the memory template
(this harness ships one in `templates/memory-template.md`) quotes `name:`
and `description:` lines in its body. Whole-file grep counts those quoted
lines as real keys and fails the file for duplicate frontmatter -- the
store's own documentation trips the gate. Bounding the parse at the
closing delimiter makes body content, fenced or not, invisible to the
checker and the index generator alike.

The bound also fails safe in the other direction: a file that does not
start with `---` yields empty frontmatter, so the exactly-one-key check
fails it hard rather than half-parsing it.

The parser is deliberately not a YAML library: the contract is single-line
scalar values only, enforced by the gate, and bash 3.2 + awk covers that.
The flip triggers are written in the script header: adopt a real parser
the day frontmatter needs nesting beyond single-line scalars, a health run
exceeds 5 seconds, or a store crosses 2000 files.

## Single sanctioned writer, notify-on-change

Exactly one scheduled process is allowed to write anything:
`memory-health-sweep.sh`. Its writes are narrow and idempotent -- one
`HEALTH.md` overwrite per store, plus a snapshot commit of the operator
store's backup repo (empty diff commits nothing). The health checker
itself is read-only by contract; the index generator writes only to stdout.

Why: recurring automation that mutates state is where unattended damage
compounds. A scheduled job that "helpfully" regenerates indexes or edits
memories will eventually do so against a store mid-edit, or after a path
moved, and each firing compounds the damage. Confining all scheduled
writes to one auditable script with an append-only output (report file,
snapshot history) caps the blast radius of every misfire at "a stale
report".

Notification discipline: the sweep raises a desktop notification only when
the report differs from the previous sweep AND carries failures or
warnings. A recurring notifier that re-announces known findings every fire
trains its operator to ignore it within a week; new-findings-only keeps
the signal alive. On systems without a notifier the exit code still
carries the result.

## Gate self-coverage in the CI path filter

The CI workflow is path-filtered so feature PRs never pay for it, but the
filter includes not just the store (`.claude/agent-memory/**`) but the
three scripts and the workflow file itself.

A gate whose own implementation can change without the gate running is a
gate that can be broken -- or quietly disarmed -- by the very PR that
breaks it. Including the tooling and workflow paths in the filter means
any PR that touches the checker, the generator, the sweep, or the gate
definition must pass the gate it just modified. Cheap, and it converts
"the gate was silently broken three weeks ago" into "this PR is red".

## The dead-man gap (known limit)

The scheduled sweep has a dead-man problem this harness documents rather
than solves: if the sweep stops firing -- the repo the scheduler points at
was moved or deleted, the checked-out branch no longer contains the
scripts, the plist was unloaded, the machine was replaced -- nothing
notices. The notification path only fires on new findings, so silence is
indistinguishable from health.

Recommended mitigations, in preference order:

- **Dedicated stable clone for the scheduler.** Point the scheduler at a
  clone used for nothing else, pinned to the default branch, at a path
  that never moves. This removes the dominant failure cause (the working
  clone being moved, rebased, or checked out to an old branch under the
  scheduler's feet).

- **Session-start freshness check.** The sweep stamps its generation time
  on the first line of each `HEALTH.md`. An agent session-start hook (or a
  shell profile line) that compares that stamp against the sweep interval
  and warns when it is older than two intervals converts silent scheduler
  death into a visible nag exactly where the operator is looking.

Both mitigations are deployment choices, not shipped code -- which
scheduler, which clone, and which session hook are all adopter-specific.
The limit itself is the portable lesson: any cron-shaped safety net needs
either a heartbeat consumer or a freshness check at the point of use,
because the failure mode of a scheduler is silence.
